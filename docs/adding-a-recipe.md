# Adding a recipe

**Short answer: yes, just drop a `.md` file into `recipes/` and push.** There is no index to
update, no registry to edit and no build step to run by hand. GitHub Actions builds the site and
deploys it, usually within a minute or two.

```bash
cp docs/recipe-template.md recipes/YourRecipeName.md
# edit it
git add recipes/YourRecipeName.md
git commit -m "Add Your Recipe Name"
git push
```

Watch it go out with `gh run list --limit 1`, or on the repository's Actions tab.

## The one thing to know

**The build validates, it does not correct.** If something is wrong it fails, names the file and
the value, and publishes nothing — the live site is left exactly as it was. So a mistake costs you
a second push, never a broken site.

Every message tells you what to fix:

```
recipes/YourRecipe.md: Category: 'Supper' is not one of the 15 known categories
recipes/YourRecipe.md: Cuisine: 'Klingon' is not one of the 13 known cuisines
recipes/YourRecipe.md: Slug: 'WrongName' does not equal the filename stem 'YourRecipe'
recipes/YourRecipe.md: Title: the '# ' heading 'Something Else' does not equal Title 'Your Recipe'
recipes/YourRecipe.md: Authors: 'TBD' is a placeholder, not a source -- name the source, or leave Authors empty
recipes/YourRecipe.md: Trailing newline: file does not end with a newline
```

Run it yourself before pushing if you'd rather not wait:

```bash
make build      # or: .venv/bin/python -m src.build
```

## What has to be true

The format belongs to [RecipeScanner](../specs/001-recipe-search-site/contracts/markdown-grammar.md),
the iOS app that also writes these files, so it is fixed. A recipe exported from that app is already
correct and needs none of this.

| Rule | Why |
|---|---|
| Filename is the slug: `YourRecipe.md` → `Slug: YourRecipe` | The filename is the recipe's identity and its URL |
| Slug is letters, digits and underscores only | It becomes `recipes.nateemma.com/YourRecipe` |
| Exactly the ten keys, in the template's order | The format is a contract; unknown keys are rejected |
| An empty key keeps its trailing space — `Tags: ` not `Tags:` | Byte-level round-trip with the app is measured against it |
| `# Title` matches the `Title:` field exactly | Otherwise the page and the data disagree |
| `Category` is one of the 15, `Cuisine` one of the 13 | See below |
| At least one real ingredient and one real instruction | A recipe should be a recipe |
| `## Notes` only if it has content | An empty heading is worse than none |
| File ends with exactly one newline | |
| `Date` is `YYYY-MM-DD HH:MM` — a space, not a `T` | |

### Categories (15)

`Appetizer` · `Baking` · `Basics` · `Breakfast` · `Brunch` · `Dessert` · `Dinner` · `Lunch` ·
`Preserves` · `Salad` · `Sauce` · `Sides` · `Snacks` · `Soup` · `Tapas`

### Cuisines (15)

`African` · `American` · `Asian` · `British` · `Caribbean` · `European` · `French` · `Indian` ·
`Italian` · `Latin American` · `Mediterranean` · `Mexican` · `Middle Eastern` · `Southwestern` ·
`Spanish`

**These lists are closed.** They come from `data/vocabulary.json`, which is generated by the
RecipeScanner project, not edited here. A vocabulary that grows by accident stops being one.

Adding one is deliberate and takes four steps:

1. Retag the recipes in `recipes/` to use the new value. The build will fail — that is correct.
2. Bump `expectedCuisineCount` (or `expectedCategoryCount`) in RecipeScanner's
   `Tools/extract-vocabulary.swift`. It is a drift guard, and it is meant to be edited by hand.
3. Run `make vocab` there. The table is *derived from this corpus*, so the new value appears
   because the recipes now use it.
4. Copy `vocabulary.json` back into `data/`, and update the two literals in
   `tests/test_vocabulary.py`.

`Caribbean` and `Latin American` were added this way, after Jamaican, Argentine, Uruguayan and
Peruvian dishes had been sitting under `American` for want of anywhere better.

## Fields worth a word

**`Authors`** is really a *source*: it holds people (`Bobby Flay`), books (`Bistronomy`),
restaurants (`Le Bec Fin`) and sites (`Serious Eats`) alike, because the format has no Book field.
Leaving it empty is fine and honest. `TBD` is not — it renders as "From TBD" and ships as an author
named TBD in the structured data.

**`Total_Time`** is free text: `45 minutes`, `2 hours`, `2 hours 30 minutes`, `3-5 hours`,
`overnight`. It drives the "under an hour" filter, and anything unparseable simply drops out of that
filter rather than failing the build.

**`Summary`** shows under the title and in search. It can be empty.

**Component groups** — an optionally named part, one level deep. The label is a bare line, then a
blank line, then its list. The same names recur under Instructions, where numbering restarts at 1:

```
## Ingredients

Walnut Cream:

- 1/2 cup walnuts
- 2 cups heavy cream

Pear Puree:

- 1 large pear
```

Group labels are detected structurally, so a label does not strictly need its trailing colon — but
including it removes all doubt. The build writes `build/parse-report.md` listing every line it read
as a label, if you ever want to check its work.

## Renaming or deleting

Rename the file and its `Slug:` together — they must match, and the old URL stops working. Deleting
is just deleting the file. Nothing else refers to it.
